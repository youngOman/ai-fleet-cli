# 設計說明

> 這份講的是**為什麼**。介面契約看 [ARCHITECTURE.md](ARCHITECTURE.md)，踩過的坑看 [pitfalls.md](pitfalls.md)。
> 每一節都是先有失敗經驗、才有現在這個設計。

## 1. 核心決策：盯「報告檔落地」，不要求 worker 主動回報

### 直覺的做法，以及它為什麼失敗

最直覺的設計是：worker 做完，自己通知指揮官。
不管是叫它跑一個 hook、給它一個「完工回報」的指令去呼叫、還是在派工單裡寫「做完請回報」——
這些**全都試過，全都會漏**。

實測到的失敗模式：

| 失敗模式 | 實際情況 |
|---|---|
| **worker 忘記** | 派工單白紙黑字寫「完成後回報」，worker 寫完程式就停在那裡不動 |
| **worker 以為自己回報了** | 它在自己的畫面上印了「已完成，回報如下」——但那只是它自己的 stdout，沒有人在看 |
| **worker 卡在輸入框** | codex 收到長訊息會停在 `[Pasted Content NNNN chars]` 不執行，連指令都沒開始跑，更不可能回報 |
| **worker context 用完** | 對話爆掉，最後那段回報永遠不會發生 |
| **worker 回報了假的** | 「review 工作流等價執行」——實際上 PR 上 0 筆 review |

根本問題是：**回報是 worker 自願行為，而 worker 是一個不可靠的執行者。**
把閉環的最後一哩路交給不可靠的一方，閉環就不成立。

實際代價：一次 worker 完工 14 分鐘沒人收，另一次完成 21 分鐘後使用者才發現「怎麼還沒開始」。
產能白白浪費，而且使用者對整套系統失去信任。

### 現在的做法

改盯一個**客觀事實**：報告檔在檔案系統上出現了。

```text
worker 完工 → 寫報告到 $FLEET_REPORTS/<YYYYMMDD-HHMM>-<id>-<主題>.md
                    ↓
        watcher 掃到新檔（或內容 hash 變了）
                    ↓  mtime 靜置 STABLE_SECS 秒才算落地
        tmux send-keys 注入指揮官輸入框
                    ↓
        指揮官被叫醒
```

差別在哪：

- 寫檔是 worker **本來就要做的事**（報告是交付物的一部分），不是額外的儀式
- 檔案存在與否是**可觀測的**，不需要 worker 誠實
- 就算 worker 中途死掉、context 爆掉、pane 被關掉，只要檔案寫下去了，通知就會發出
- watcher 不在 worker 的行程裡，worker 卡死不影響通知路徑

這條「不改成 worker 主動回報」是**明確不做**的第一條。
任何想「優化」成 worker 直接推送的提案，都要先能回答上表那五個失敗模式。

### 為什麼還要有「閒置」與「卡住」兩個訊號

盯報告檔只能抓到「有交東西」。剩下兩種病態要另外抓：

- **做完了但沒寫報告**（worker 忘了那一步）→ 由 busy 轉 idle 一段時間、且近期沒有報告 → ⚠️ 閒置
- **根本沒開始跑**（訊息卡在輸入框）→ `stuck` 訊號持續一段時間且非 busy → 🚧 卡住

這兩個是**推測性**訊號，會有偽陽性，所以門檻設得比報告訊號保守（90 秒 / 60 秒），
而且「卡住」硬性要求非 busy——忙碌中訊息排隊是正常現象，不是卡住。

## 2. 資料流

```text
                 ┌──────────────────────────────────────────┐
                 │  $FLEET_REPORTS/                          │
   worker cc1 ──►│    20260803-1420-cc1-refactor-auth.md     │
   worker cx1 ──►│    20260803-1431-cx1-verify-auth.md       │
                 └───────────────┬──────────────────────────┘
                                 │ 掃描（週期性）
                                 ▼
        ┌────────────────────────────────────────────────────┐
        │  libexec/fleet-watcher（bash，背景常駐）             │
        │                                                     │
        │  A. 報告路徑                                         │
        │     plan-reports ──► libexec/fleet-state（python3） │
        │       · mtime 靜置 STABLE_SECS 才算落地             │
        │       · hash 比對：同檔內容沒變不重送                │
        │       · backfill：首見的舊檔只建基準線               │
        │       · attempts：連 3 次驗不到就熔斷                │
        │                                                     │
        │  B. worker 路徑                                      │
        │     capture-pane ──► lib/signals.sh                 │
        │       · autoreplyN 命中 → 送按鍵，本輪到此為止      │
        │       · 讀 adapters/<kind>.conf 判定 busy/stuck     │
        │     worker-tick ──► fleet-state                     │
        │       · busy→idle 計時、stuck 計時、去重旗標         │
        └───────────────┬────────────────────────────────────┘
                        │ 有事要通知
                        ▼
        ┌────────────────────────────────────────────────────┐
        │  lib/tmuxio.sh :: send_verified                     │
        │    1 取消 copy-mode                                 │
        │    2 TUI 沒起來 → 不送不記帳（下輪再試）             │
        │    3 使用者正在打字 → 不送不記帳（不插隊）            │
        │    4 send-keys -l  →  sleep  →  Enter               │
        │    5 capture-pane | grep 短單號 驗證送達             │
        └───────────────┬────────────────────────────────────┘
                        │ rc=0 送達 / 1 驗不到 / 2 使用者打字 / 3 沒 TUI
                        ▼
                 ┌──────────────────────────┐
                 │  指揮官 pane（輸入框）     │
                 │  📥 cc1 交報告 … (r…)     │
                 └──────────────────────────┘
                        │ 只有 rc=0 或 rc=1 才回寫
                        ▼
                 record-report / record-worker ──► state.json
```

關鍵在於**回傳碼的四分法**。「沒送」跟「送了但驗不到」是完全不同的事：

- `2`（使用者在打字）、`3`（TUI 沒起來）是**環境暫時不允許**，不是失敗——不記 attempt，下輪原樣重試
- `1`（驗不到）才是真失敗，記一次 attempt，累積到上限就熔斷

如果把 2 / 3 也算成失敗，通知會在 worker 重啟或使用者打字的期間被熔斷掉，**永久遺失**。

## 3. registry 為什麼用 `%NN` 而不是 `0:1.2`

tmux 有兩種定位 pane 的方式：

| 寫法 | 例子 | 性質 |
|---|---|---|
| 座標 | `0:1.2` | session:window.index——**相對位置** |
| pane id | `%12` | tmux 分配的**穩定唯一 id**，pane 活著就不變 |

早期用座標，然後就出事了：使用者在 window 中間插了一格新 pane，
後面所有 pane 的 index 整排位移，registry 裡的 `cc1` 突然指到別人身上——**派工送錯人**。

這種錯特別惡劣，因為它**不會報錯**。訊息送出去了、驗證也過了，只是送給了錯的 worker。
你要等到那隻 worker 開始亂改一個不相干的 repo 才會發現。

改用 `%NN` 之後：

- 開關其他 pane 不影響既有 pane 的 id
- pane 死掉，`%NN` 就整個查不到——變成**明確的失聯**，而不是靜默的錯誤定址
- `fleet discover` 直接吐 `%NN`，使用者不用自己數格子

同理，registry 也記 socket。adopt 進來的 pane 在使用者的預設 socket，
spawn 出來的在 `FLEET_SOCKET`（預設 `agents`），兩邊 pane id 各自獨立編號，
**只有 `(socket, pane)` 這一組才唯一定址**。所有 tmux 呼叫都必須帶 socket——
包括通知指揮官那條路徑。舊版通知用裸 `tmux`，指揮官只要不在預設 socket 就全部靜默失敗。

## 4. `fleet task` 為什麼送短訊指向 brief 檔

派一張正式任務單，內容通常是幾十行：目標、背景、邊界、驗收條件、回報格式。
直覺做法是把整段 heredoc 直接 `send-keys` 進去。

**這對 codex worker 會壞掉。**

長訊息貼進 codex 的輸入框，它不會展開成文字，而是折疊成
`› [Pasted Content NNNN chars]` 然後**停在那裡不執行**。
更糟的是——`fleet send` 這時候**回報成功**，因為對 tmux 來說「貼上」確實完成了。
這是徹底的**假訊號**：你以為派了，實際上什麼都沒跑。

（同一天在三個不同的 codex worker 上重現過；claude worker 沒有這個問題，但沒理由賭。）

所以 `fleet task` 的做法是：

1. 派工單以檔案形式放在 `$FLEET_TASKS/<brief>.md`
2. 只送**一句短訊**：請讀 `<brief 的路徑>` 並依其執行，完成後把報告寫到 `<報告目錄>`
3. worker 自己用它的檔案讀取工具去讀

這樣做的附帶好處，其實不比避開 bug 小：

- **派工內容有版本可回溯**——事後能追「當初到底是怎麼交代的」，而不是靠翻 tmux scrollback
- **不受 TUI 輸入框長度／折行／特殊字元影響**——短訊永遠貼得進去
- **驗證變簡單**——`send_verified` 只要 grep 一個短單號就好（見下節）
- **派工單可以重用**——同一份 brief 派給不同 worker 做交叉驗證

### 附帶：為什麼驗證只 grep 短單號

送出後要確認訊息真的進了輸入框，做法是 `capture-pane` 回讀再 grep。
但**不能 grep 整句**：TUI 會依 pane 寬度折行，一句話在畫面上被切成好幾段，
中間插入換行與縮排，全文比對必定失敗。

所以每則通知都帶一個短單號（例如報告訊號用 `r<mtime>`），
grep 只找這個短單號——它夠短，不會被折行切開。

## 5. 訊號規則為什麼是資料檔而不是程式碼

判斷一個 worker 是「跑中／閒置／等答／卡住」，靠的是對 `capture-pane` 的輸出做 regex 比對。

第一版把這些 regex 直接寫在程式裡。結果同一份 regex 被複製到了 **4 個檔案**
（CLI 的看板、watcher、mon、狀態判定），然後就開始漂移——
改了 watcher 的忙碌判定，忘了改看板的，於是看板說閒置、watcher 說在跑，兩邊互相打臉。

現在規則集中在 `adapters/<kind>.conf`，純 `key=value`：

```ini
busy=esc to interrupt|without interrupting|shell still running|Running [0-9]+ shell
stuck=Press up to edit queued messages|\[Pasted Content [0-9]+ chars\]
```

`lib/signals.sh`、`libexec/fleet-mon`、`libexec/fleet-state` 都從這一份讀，**regex 只有一份**。

這個決定順帶解決了三件事：

1. **新增 worker CLI 不用改程式碼。** 想支援第三種 AI CLI？寫一個新的 `.conf` 就好。
   判定 kind、忙碌訊號、就緒訊號、context 百分比擷取全在裡面。
2. **可測。** fixture 是錄下來的真實 pane 快照，adapter 是資料，
   測試就是「這份快照 × 這份 conf ＝ 應該判成 busy」，不需要跑 tmux。
3. **使用者可以自己調。** 上游 CLI 改了介面文案，使用者改一行 conf 就能救，
   不用等這個 repo 發版。

值限定為 ERE（`grep -E` 與 python `re` 的交集語法），因為 bash 側用 `grep -E`、
python 側用 `re`，寫成任一方獨有的語法都會在另一邊爆炸。

## 6. 為什麼要有自動應答

### 問題：一個沒人回答的對話框可以廢掉一整晚

回報閉環讓 worker 完工時能叫醒指揮官。但有一種停擺是閉環抓不到的——
**worker 沒有完工，也沒有在跑，它在等一個沒有人會回答的問題。**

實際案例：codex 跑到一半彈出「Retry with a faster model?」的攔截框。
這個框在等一個按鍵。指揮官不在（他正在等這隻 worker 交報告），
使用者也不在（他是去睡覺才開整晚艦隊的）。於是：

- worker 不 busy（它沒在跑）
- worker 也沒有 `stuck` 訊號（那是輸入框卡訊，不是對話框）
- 它就在那裡待到天亮

「⚠️ 閒置未交報告」最終會發出來，但那是 90 秒後、而且只是把人叫醒去手動按一個鍵——
如果沒人在，就是一整晚。

### 解法：可設定的自動應答

watcher 每輪巡邏抓 worker 畫面時，先比對 adapter 定義的自動應答規則。
命中就送出對應按鍵再送 Enter：

```ini
# adapters/cx.conf
autoreply1_match=Retry with a faster model
autoreply1_keys=2
```

`N` 從 1 到 9，可以定義多組。這一樣是**資料不是程式碼**——
你的 CLI 有別的攔截框，加兩行 conf 就好，不用改 watcher。

### 三個設計細節

**1. 為什麼答案要寫在 conf 裡，而不是「一律選預設」。**
因為預設常常是錯的。上面那個框的預設是「好，降級到快模型」——
它會**默默降低整批工作的品質**，而且沒人知道。
選 `2`（不要，等強模型）是一個**明確的策略決定**，
所以它必須是使用者寫下來的值，不能由工具猜。

**2. 命中的那一輪跳過狀態判定。**
按鍵送出去之後畫面正要重繪，這一瞬間抓到的畫面既不能代表 busy 也不能代表 idle。
在這裡做判定只會產生垃圾狀態轉換，甚至誤發「閒置」通知。
所以命中自動應答就 `continue`，等下一輪畫面穩定了再說。

**3. 這是「代答」，不是「代決策」。**
自動應答只處理**已知的、答案永遠一樣的**攔截框。
凡是需要看情況決定的問題（「要不要刪這個檔案？」），
一律走 `asking` 訊號讓指揮官自己去看——那不是自動應答該碰的東西。
規則寫得太寬，等於讓 watcher 替你亂點確認鍵。

## 7. 為什麼設定檔是 `config.env` 而不是 TOML

原始規格寫的是 `~/.config/fleet/config.toml`，實作**刻意沒有照做**。
這是與規格的明確偏離，理由如下。

### bash 沒有可靠的 TOML parser

這個工具的核心必須是 bash——tmux 的互動（`send-keys`、`capture-pane`、
copy-mode 判定）只能在 bash 側做。設定值要在 bash 讀得到，
所以 parser 也得在 bash 側。

而用 `sed` / `awk` 手寫一個 TOML parser 是 **bug 工廠**。
TOML 有多行字串、陣列、inline table、巢狀 table、四種跳脫規則、
還有註解與值裡的 `#` 要區分。每一項都是一個等著咬人的邊界情況，
而且失敗模式很惡劣：**parser 靜默解錯一個值，工具就用錯設定跑**，
你要很久以後才會發現。

替代方案是引入相依（外部 TOML CLI、或 python 套件）。但目前整包的相依是
tmux + python3 + bash 3.2，全部是系統內建——**為了讀設定而破壞這件事不划算**。

### 設定內容本來就是扁平的

看一下實際要存什麼：路徑、socket 名、一堆秒數門檻。
全部是 `FLEET_*` 開頭的**純量**，沒有一個需要結構。
TOML 的表達力在這裡完全用不上，只是白付 parser 的代價。

### `KEY=value` 可以被安全地驗證

這是關鍵。設定檔是一個**執行程式碼的風險點**——
最偷懶的 bash 讀設定寫法是 `source config.env`，
那等於讓設定檔裡任何一行變成任意程式碼執行。

現在的載入器不 `source`，逐行解析並套三條規則：

1. **key 必須是 `FLEET_` 開頭的大寫名稱**——設定檔改不了 `PATH`、`LD_PRELOAD`、`IFS`
2. **值不得含反引號或 `$(`**——擋掉命令替換
3. **已存在於環境的 key 不覆寫**——真實環境變數優先

不符合的行**拒絕載入並印警告**，不靜默忽略。

這三條規則用幾行 bash 就能寫對，而且**任何人都看得懂它為什麼安全**。
一個「大致能動」的 TOML parser 給不了這個保證。

### 代價

設定檔不能放結構化資料。目前不需要——
真正需要結構的東西（adapter 的訊號規則）已經有自己的檔案格式了，
而那個格式同樣是刻意扁平的 `key=value`，理由完全一樣。

## 8. 狀態為什麼集中在單一 `state.json`

舊版的狀態是**一堆散檔**：

```text
.state/
  rep-20260803-1420-cc1-xxx.notified    ← 這份報告通知過了（內容是 mtime）
  rep-20260803-1420-cc1-xxx.hash        ← 上次通知時的內容 hash
  worker-cc1.wasbusy
  worker-cc1.idle_notified
  ...
```

問題一個一個來：

**1. 檔名轉碼會撞 key。**
散檔要把報告檔名塞進檔名，所以做了 `tr -c 'A-Za-z0-9_.-' '_'` 逐 byte 轉碼。
中文主題整串被壓成 `_`——`20260803-1420-cc1-重構驗證.md` 和
`20260803-1430-cc1-補測試.md` 轉出來是同一個 key，
**後面那份報告被永久靜音**。而且 UTF-8 是逐 byte 轉，一個中文字變三個底線，長度還會爆。
JSON 的 key 本來就吃 UTF-8，改用 JSON 之後這個 bug 直接消失——
**key 就是檔名原文，不做任何轉碼**。

**2. 沒有原子性。**
一次通知要更新 `.notified` 和 `.hash` 兩個檔。中間 watcher 被 kill，
就留下「通知過但 hash 是舊的」的半殘狀態，下一輪重送。
單一 JSON 用 temp + rename 原子寫入，要嘛全成功要嘛全沒發生。

**3. 沒辦法一眼看全貌。**
除錯時想知道「現在系統覺得什麼事情發生過」，要 `ls` 一個目錄然後逐檔 `cat`。
現在 `fleet-state dump` 一次吐出整份 pretty JSON。

**4. 清不掉的垃圾。**
報告刪了、worker forget 了，散檔還躺在那裡，一年後幾千個檔案。
現在 `fleet gc` 掃一遍就把不存在的報告 entry 和不在 registry 的 worker 清掉。

**5. schema 沒有版本。**
散檔的格式是「檔名後綴 + 檔案內容」，加欄位就是加一種後綴，沒人知道現在有幾種。
JSON 有 `"version": 1`，之後要改結構有地方掛遷移邏輯。

搭配這個決定的是：**只有一個程式可以寫 `state.json`**——`libexec/fleet-state`。
bash 側（watcher）永遠透過它的子命令讀寫，不自己碰 JSON。
這樣併發控制與原子寫只需要在一個地方做對，而且狀態機邏輯是 python，**可以測**。
